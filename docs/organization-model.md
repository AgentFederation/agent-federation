# 组织模型与概念辨析

状态：设计假设，尚未实现验证。模型面向目标、交付与反馈可表达的数字协作组织；不声称覆盖所有人类组织。

## 组织闭环

持续目标与环境事实使成员发现工作；成员按职责协作并形成真实结果；结果更新共享事实，影响后续行动与组织自身的做法。一次任务结束，只结束一次工作，不结束持续责任。

模型使用目标、职责、成员、任务、共享状态与证据、协作规则六个概念，定义见项目 README。任务的一次执行另记为 Run：成员是协作身份，runtime 是执行工具，节点是部署位置。这三个概念不能合并。

## AI 为什么需要职责和成员

人类因技能差异、注意力有限、责任归属与协调成本而分工。AI 可以复制与切换模型，因此不能直接照搬固定岗位、固定人数或层级管理。但上下文有限、工具能力不同、并发工作有依赖、结果需要有人持续承接，这些约束仍然存在。

职责的候选价值是让“当前没有任务但仍需关注的结果”有归属；成员的候选价值是让跨次执行的上下文、交接关系与责任可以延续。二者都不要求固定绑定某个 runtime，也不要求固定主管层级。

替代模型可以只有目标、任务与执行池。如果它同样能清楚表达持续责任和跨次协作，且更简单，就应简化现有模型。POC 要观察这些概念是否帮助解释真实行为，而不是仅验证数据表存在。

## 自主改进

复盘读取失败、返工、未采用结果和消耗等证据，输出建议、不改或证据不足。统筹决定处理方式；采纳后成为普通改进任务，实施后再次检查效果。报告完成不等于改进完成，改动完成也不等于有效。

改进应说明问题证据、最小改动、预期收益和检查条件，允许删除、简化或保持现状。偶发材料缺失不应自动升级为建设新平台。

## 通用性的证据边界

更换 runtime 只证明执行器可替换；一个 X 场景跑通只证明该场景可用。当前采用“双场景设计、单 POC 实施”：设计同时以 X 运营和闲鱼服务经营评审，实际优先实现 X。详见[设计评审用例](design-review-cases.md)。

闲鱼用例重点检验多客户并行、外部输入等待、交付修订和经营反馈。纸面评审提供设计覆盖证据，实际跨场景可用性仍待实现验证。软件维护小组作为未来候选反例保留，不要求当前再落地一个项目。需要在内核写入具体业务分支时，应重新检查抽象边界。
