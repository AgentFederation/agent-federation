# 首个 POC：持续运营一个 X 账号

状态：待实现。此处描述可公开复用的验证场景，不包含账号身份、私有材料或配置凭据。

## 团队与场景

五个固定成员分别承担运营统筹、内容与发布、关系运营、评论与对话、运行复盘。前四个初始使用 Codex，复盘初始使用 DeepSeek harness；职责与执行配置分离。复盘成员只读取证据并提出判断，不需要浏览器；统筹决定是否采纳并安排实施。

1. 到运营窗口，成员读取目标、已有结果与未完事项，安排并开展实际工作。
2. 内容、关系和评论职责独立推进，不人为串成固定流水线。
3. 评论成员发现材料缺口，记录来源；内容成员承接补充，评论成员等待该结果并可继续其他独立工作。
4. 材料交付后，评论成员实际采用并回复，记录材料版本和业务结果。
5. 复盘成员读取问题与执行证据，提出改进、不改或证据不足的判断；统筹安排处理。
6. 采纳的改进落实到具体工作，并在后续运营检查效果；下一窗口无需人工重新派活。

启用时直接真实使用，不另设分段接管课题。现场未发生的情境可用明确标注的历史记录回放；不制造平台互动来凑验证。

## 核心验收

| 核心 | 可核对的证据 |
| --- | --- |
| 持续运营接续 | 无需逐次人工派活；未完事项保留；按条件继续或等待；任务结束后仍有明确后续检查 |
| 有效成员协作 | 问题来源、承接成员、交付物、接收与实际采用结果可追溯；缺少交付时不能直接完成 |
| 自主复盘改进 | 有证据的问题走完判断、最小实施、效果检查与处理决定；仅报告建议不算通过；正常情境允许不改 |

改进无效后据证据撤回也是有效闭环，不要求每次优化成功。需要有真实或明确标注回放的完整改进实例，不能只靠“不改”证明改进能力。

在预先约定的完整运营窗口保留全部尝试、失败与人工介入，不能只挑一次成功。具体窗口和回放批次尚待实际工具与运营节奏确定；当前不宣称稳定性通过。

## 两个架构探针

- 同一复盘职责与证据分别交给 DeepSeek harness、Codex，仅改分配配置；均能按共同合同被接收，不改组织流程。换模型不等于换 runtime。
- 执行节点经统一接口取任务、取材料、交回结果；若要声称跨机器通过，实际在第二台机器运行。同机分进程只验证接口边界。

## 三个技术重点

| 难点 | POC 最小处理 |
| --- | --- |
| 执行结束、失败或未回报时如何接续 | 持久化任务、执行与下一检查条件；重启接续；未知结果先核对 |
| 独立成员与异构 runtime 如何可靠交接 | 统一输入输出和证据引用，装配必要上下文，先接通两个 runtime |
| 反馈如何产生有价值的后续工作 | 记录行动、等待或不行动的依据；必要行动成为任务；改进有效果检查 |

下一步细化成员最小执行合同，并核实两个 runtime 与现有业务工具的实际接口。尚未验证 DeepSeek harness 的具体接入实现。

## 范围

先验证固定团队、持久状态、异构执行与持续闭环。动态增员、多机高可用、全面 harness 兼容与管理后台后置。自主优化优先作用于职责说明、交付要求和步骤；任意自动改写并发布系统不是前提。

场景通过不代表增长或营收已证明，也不代表所有组织都可运行。跨领域通用性需要额外对照证据。
